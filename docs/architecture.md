# HireLens Architecture Specification

## 1. System Overview

HireLens is a college-focused recruitment and assessment platform architected as a **modular monolith** with decoupled asynchronous background workers, designed to reliably serve approximately 200 college students initially, with clear paths to scale.

The platform prioritizes:
- Deterministic business logic over unbounded LLM autonomy.
- Verification and explainability at every layer.
- Zero mock data in production surfaces.
- A strict frontend language policy (no internal AI or framework jargon exposed to end-users).

## 2. Component Responsibilities

### 2.1 Web Frontend (`/frontend`)
- **Technology**: Next.js (TypeScript, React 18/19, Tailwind CSS).
- **Aesthetic**: Clean, academic-recruitment design language (Deep Navy `#0F172A`, Primary Blue `#2563EB`, neutral light backgrounds, subtle borders, data tables, detail drawers, timelines).
- **User Language**: All UI copy is strictly professional and user-centric (e.g., "Resume Match: 84%", "Assessment Integrity: Active"). Technical terms like *FastAPI*, *embeddings*, *MediaPipe*, *YOLO*, *OCR* are forbidden in normal user-facing views.
- **Client-Side Telemetry**: Captures window blur, tab switches, and webcam frame monitoring with on-device detection to avoid continuous video transmission.

### 2.2 Backend Application (`/backend`)
- **Technology**: Python 3.12, FastAPI, Pydantic v2, SQLAlchemy / asyncpg.
- **Role**:
  - Authenticates users via verified institutional email.
  - Enforces strict Role-Based Access Control (`STUDENT`, `RECRUITER`, `COLLEGE_ADMIN`).
  - Implements deterministic state machines for drives, applications, resumes, and assessments.
  - Generates pre-signed short-lived S3 URLs for secure document upload and viewing.
  - Calculates candidate matching and integrity scores deterministically.
  - Exposes `/health` and `/readiness` checks.

### 2.3 Database (`Supabase PostgreSQL`)
- **Role**: System of record for 25+ relational entities.
- **Security**: Supabase Row Level Security (RLS) ensures students access only their own submissions, recruiters access only applicants to their drives, and college admins access institutional summaries.
- **Integrity**: Strict foreign key constraints, unique constraints preventing duplicate applications or submissions, and check constraints on score ranges.

### 2.4 Object Storage (`Amazon S3`)
- **Role**: Private object store for uploaded candidate resume PDFs.
- **Access Model**: Public access is completely blocked. All uploads and downloads occur through short-lived presigned URLs (15-minute expiration) generated by authorized FastAPI endpoints.

### 2.5 Cache & Job Queue (`Upstash Redis`)
- **Role**: Distributed cache and queue backend for background asynchronous processing.
- **Queued Operations**: Heavy PDF extraction, OCR fallback, Groq question generation, embedding calculation, email dispatch.

### 2.6 Background Workers (`/workers`)
- **Technology**: Python worker processes subscribing to Redis task queues.
- **Behavior**: Idempotent task execution with explicit job states (`QUEUED`, `PROCESSING`, `COMPLETED`, `FAILED`, `RETRYING`). Never leaves jobs indefinitely hanging in `PROCESSING`.

### 2.7 AI / ML Engines (`/ai`)
- **Resume Extraction**: PyMuPDF for native PDF text blocks; Tesseract OCR for scanned PDF fallback.
- **Canonical Skill Normalization**: Exact alias dictionary lookup + fuzzy token matching against canonical skill taxonomy.
- **Semantic Matching**: Sentence-Transformers (`sentence-transformers/all-MiniLM-L6-v2`) for computing semantic cosine similarity between job descriptions and resume text evidence.
- **MCQ Generation**: Groq LLM API with strict Pydantic schema validation, distractor verification, and deduplication.
- **Integrity Signals**: Client-side MediaPipe for face presence/count; lightweight YOLO for prohibited objects.

## 3. Communication Patterns

1. **Synchronous HTTP**:
   - Client to Backend for navigation, profile updates, drive browsing, application submission, assessment response submission, and score reviews.
2. **Asynchronous Background Jobs**:
   - Heavy tasks (resume ingestion, AI question generation, email dispatch) receive a `job_id` with `202 Accepted`. The client polls job status or listens to state changes.
3. **No Direct Frontend-to-Database**:
   - The Next.js frontend interacts with Supabase strictly via FastAPI backend endpoints, enforcing backend business authorization and audit logging.
